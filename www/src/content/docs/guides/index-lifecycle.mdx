The engine handle exposes lifecycle methods. They write through
`@siftlite/fts5` and the `__sift_registry` table.

```ts
await index.create();
await index.rebuild();
const check = await index.check();
const doctor = await index.doctor();
await index.drop();
```

You can call the same operations without the engine:

```ts
import { checkIndex, createIndex, doctorIndex, dropIndex, rebuildIndex } from "@siftlite/fts5";

await createIndex({ adapter, definition });
```

## `create`

Materializes physical FTS (and optional trigram) objects, linked triggers
when `mode: "linked"`, and a healthy registry row. If a **healthy** index
already exists, it throws `SEARCH_CONFIG_INVALID` with
`reason: "already-exists"`.

A `pending` registry row is treated as interrupted maintenance: SiftLite
tries to finish or rematerialize rather than leave a half-built generation
searchable.

## `rebuild`

Replaces physical objects. This is a maintenance operation. Concurrent
readers may see a gap depending on the adapter's transaction story. D1
`batch()` is sequential, not interactive `BEGIN`/`COMMIT`.

## `check` / `doctor`

- `check()` → `{ ok, findings }`
- `doctor()` → `{ healthy, findings, registry }`

Findings use `severity: "info" | "warn" | "error"`. Branch on codes, not
message text.

## `drop`

Removes physical objects and the registry row. Destructive. The CLI
equivalent requires `--acknowledge`.

## Registry

`REGISTRY_TABLE` is `__sift_registry`. Search refuses to run unless the
row exists and `health === "healthy"`.

There are two initial materialization paths:

1. Runtime path: call `create()` / `createIndex` after the source table exists.
2. Migration path: apply Drizzle/Prisma companion SQL, which creates objects
   and seeds a `pending` row, then call `createIndex` once with the same
   definition to verify and mark it `healthy`.

For an intact pending generation, `createIndex` reuses the migrated objects.
If maintenance was interrupted or objects are incomplete, recovery can
rematerialize them. Calling it again after the row is healthy throws
`SEARCH_CONFIG_INVALID` / `already-exists`.

<Aside type="caution" title="Typo fallback and companion SQL">
In `0.1.0`, `compileIndexLifecycleSql` does not emit the trigram table required
by `typoTolerance.mode: "fallback"`, and integrity checks do not detect that
omission. Use the runtime path for fallback-enabled definitions.
</Aside>

## Secure delete

`createFts5Engine({ adapter, secureDelete })` accepts `"off"` (default)
or `"required-if-supported"`. FTS5
[`secure-delete`](https://www.sqlite.org/fts5.html#the_secure_delete_configuration_option)
is a persistent table configuration introduced in SQLite 3.42.0, so SiftLite
probes and version-gates it at runtime. Provider Time Travel, replicas, and
backups are outside search-visibility deletion.
