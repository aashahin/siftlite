<PackageManagers pkg="@siftlite/drizzle" />

Tested against `drizzle-orm@0.45.2` metadata: `getTableName`,
`getTableColumns`, column `name` / `dataType` / `columnType`, timestamp
`mode`.

```ts
import { bunSqliteAdapter } from "@siftlite/bun";
import { defineDrizzleIndex, drizzleSearch } from "@siftlite/drizzle";
import { createIndex } from "@siftlite/fts5";

const articlesSearch = defineDrizzleIndex(articles, {
  id: articles.id,
  searchable: { title: { weight: 1 } },
  filterable: { status: articles.status },
});

await createIndex({ adapter, definition: articlesSearch.definition });
const result = await drizzleSearch(db, articlesSearch, adapter).search("drizzle", {
  hydrate: true,
});
```

Unsupported Drizzle types (`blob`, `bigint`, JSON blobs) fail at definition
time. Timestamp columns use Drizzle's explicit `timestamp` / `timestamp_ms`
mode; generic integers are not guessed to be dates.

## Companion SQL

```ts
import { generateDrizzleSearchSql } from "@siftlite/drizzle";

const migration = generateDrizzleSearchSql(articlesSearch);
```

`generateDrizzleSearchSql` forwards `compileIndexLifecycleSql`, so the
fragment includes `__sift_registry` DDL when that compiler emits it. Search
still requires a healthy registry row. After the source table exists, call
`createIndex` and then `drizzleSearch`. Applying companion SQL alone is not
enough, and applying it then calling `createIndex` rematerializes the same
physical objects.

Canonical escape hatch: `articlesSearch.definition`.

See `examples/drizzle-bun`.
