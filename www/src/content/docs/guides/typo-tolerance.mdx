Typo fallback is **opt-in on the definition** and still **capability-gated**
at search time.

```ts
typoTolerance: { mode: "fallback" }
```

Default is `{ mode: "off" }`. The only other accepted mode is `"fallback"`.

## What "fallback" means

1. The exact FTS5 query runs first.
2. If it returns no hits, SiftLite may retrieve trigram candidates and
   score them with Damerau-Levenshtein, within a bounded policy.

It is not always-on fuzzy matching and it does not rewrite the user's
query into FTS5 `OR` fuzz.

## Requirements that all have to hold

- Definition `typoTolerance.mode === "fallback"`.
- Runtime probe `trigramTokenizer === true`.
- Search policy does not disable it.

Default search policy is
`typoFallback: "disabled-on-cost-sensitive-runtimes"`. D1 adapters set
`costSensitive: true`. If the definition requests fallback under that policy,
search throws `SEARCH_CAPABILITY_UNSUPPORTED` /
`typo-fallback-unsupported`; it does not run exact-only search. Keep the
definition mode `"off"` unless you pass an explicit policy that enables it
**and** accept the cost.

```ts
createFts5Engine({
  adapter: d1Adapter(env.DB),
  policy: { typoFallback: "enabled", costSensitive: true },
});
```

That combination is a deliberate policy decision. `D1_DEFAULT_SEARCH_POLICY`
rejects fallback-enabled definitions by default.

<Aside type="danger" title="0.1.0 correctness limitation">
The fallback candidate query currently does not apply the request `filter`,
bound `scope`, or field sort. Fuzzy hits also do not feed `totalHits`, facets,
highlighting, or the exact-query `page.hasMore` value. Do not enable fallback
for tenant isolation, authorization filters, or any query where those response
fields must describe the fuzzy result set. Keep `mode: "off"` until the
fallback pipeline preserves the same request semantics.
</Aside>

## Bounds

Declared `DEFAULT_FUZZY_POLICY` values:

| Limit | Value |
| --- | --- |
| `minTokenCodepoints` | 3 |
| `maxQueryTokens` | 4 |
| `maxTrigramsPerToken` | 24 |
| `minGramOverlap` | 1 |
| `maxCandidates` | 200 |
| `maxEditDistance` | 2 |

`maxEditsForToken` further caps edits by token length. When fallback runs
and you pass `diagnostics: true`, `response.meta.fuzzyUsed` is `true`.

The current search path enforces the token, trigram, candidate, and edit
distance caps, but it does **not** use `minGramOverlap`; candidate retrieval is
an OR across generated grams. `ApplicationLimits.maxFuzzyCandidates` is also
not wired into this path in `0.1.0`; the effective candidate cap is the fixed
`DEFAULT_FUZZY_POLICY.maxCandidates` value.
