SiftLite will not claim a feature is available because FTS5 can do it on
some other runtime. Effective capabilities are:

**backend semantics ∩ runtime features ∩ runtime limits ∩ probes ∩ policy**

`@siftlite/fts5` advertises `FTS5_BASE_CAPABILITIES` (full text, phrase,
prefix, weighted ranking, highlight, snippet, filters, sort, facets, typo
fallback, vocabulary). Runtime adapters then constrain that set.

## Policy

Pass a `SearchPolicy` into `createFts5Engine`:

```ts
typoFallback: "enabled" | "disabled" | "disabled-on-cost-sensitive-runtimes"
costSensitive?: boolean
```

When `policy` is omitted, search uses
`{ typoFallback: "disabled-on-cost-sensitive-runtimes" }`. Combined with a
cost-sensitive adapter (D1, remote libSQL), a definition with
`typoTolerance.mode: "fallback"` is unsupported: search throws rather than
silently falling back to exact-only behavior.

Typo fallback also requires a proven trigram tokenizer probe. If the effective
capability is false for either policy or probe reasons, search throws
`SEARCH_CAPABILITY_UNSUPPORTED` / `typo-fallback-unsupported`.

## Runtime limits

Each adapter exposes `runtimeCapabilities.limits` (`maxBindParameters`,
`maxStatementBytes`, `maxLikePatternBytes`, and so on). Compilers reserve
budget before the statement is sent. Hitting a proven limit raises
`SEARCH_RUNTIME_LIMIT_EXCEEDED` or `SEARCH_QUERY_LIMIT_EXCEEDED`.

Application limits (`DEFAULT_APPLICATION_LIMITS`) cap query length, term
count, page size, filter depth, and facet count independently of the
database.

## Consistency

Read-your-writes is an adapter fact, not a search-API promise. A plain D1
binding is **not** session-aware and is not replica-eligible
(`readReplicaEligible: false`). Cloudflare documents read replication through
Sessions; `d1SessionAdapter` sets `readReplicaEligible: true` and sequential
session consistency. SiftLite does not infer cross-request continuity from a
plain binding. See [Cloudflare D1](/adapters/d1).
